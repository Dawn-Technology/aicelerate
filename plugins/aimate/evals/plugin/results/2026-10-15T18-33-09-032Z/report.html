### IMP-1 — Data model for imports and rejected rows
**Size:** S · **Depends on:** none

- Add an `import_jobs` table: id, account_id, user_id, status (`queued` / `processing` / `completed` / `failed`), file reference, total_rows, imported_count, rejected_count, timestamps, error_message.
- Add an `import_rejections` table: job_id, row_number, the raw row values, reason_code, and a reason message.
- Add a unique index on contacts `(account_id, normalized_email)`. This is the backstop that stops two imports running at once from both inserting the same contact.

**Acceptance criteria**
- Migrations run forward and back cleanly.
- If the contacts table already has duplicates, the index migration finds them and reports them instead of failing partway.

---

### IMP-2 — Upload endpoint (async handoff)
**Size:** M · **Depends on:** IMP-1

- `POST /contacts/imports` accepts the file, stores it in object storage, creates an `import_jobs` row with status `queued`, puts a job on the queue and returns **202** with the job id.
- It checks only what's cheap: file size limit, content type, readable encoding, and a header row containing `name`, `email`, `city`. It does no row-by-row work.
- **[Assumption]** Files over 50,000 data rows are rejected outright, not cut off at 50,000. The worker checks the count; the endpoint only enforces the size limit.

**Acceptance criteria**
- Responds in under about 1s for a 50k-row file.
- Bad headers or a wrong file type return 400 with a clear message.
- Requests without auth or permission are rejected.

---

### IMP-3 — Row validation rules
**Size:** S · **Depends on:** none (can run in parallel)

- Write a pure function that takes a row and returns either a normalized contact or a rejection reason.
- Email: trim it, check the syntax, and lowercase it for comparison.
- Name and city: trim them. Whether they're required is open question 3.
- Use stable reason codes such as `INVALID_EMAIL`, `MISSING_FIELD`, `DUPLICATE_EXISTING`, `DUPLICATE_IN_FILE`.

**Acceptance criteria**
- Unit tests cover valid and invalid emails, whitespace, unicode, empty cells, extra or missing columns, and quoted fields with commas or newlines.

---

### IMP-4 — Background import worker
**Size:** L · **Depends on:** IMP-1, IMP-2, IMP-3

- Read the stored file as a stream. Don't load all 50k rows into memory.
- Work in batches of about 500–1,000 rows. For each batch:
  - validate each row (IMP-3)
  - look up existing emails for the account in one query
  - check for duplicates against emails seen earlier in the same file
  - bulk insert using insert-or-skip-on-conflict, and record any conflicts as `DUPLICATE_EXISTING`
  - write the rejected rows
  - update the job's progress counters
- Set the job status to `completed` or `failed`, recording an error message on failure.
- Idempotency: if the worker crashes and the job is retried, it must not create double inserts or double rejections. Either resume from the last committed batch or make the batches idempotent.

**Acceptance criteria**
- A 50k-row file with mixed valid, invalid and duplicate rows ends with `imported + rejected = total`.
- Killing the worker partway and retrying gives the same final result.
- Memory use stays roughly flat regardless of file size.

---

### IMP-5 — Isolation so imports don't block the API
**Size:** M · **Depends on:** IMP-4

- Run imports on their own queue and worker pool, separate from the request-serving processes.
- Limit concurrency per account (e.g. one active import per account) and globally. **[Assumption]** A second upload while one is running is queued, not rejected.
- Keep each database transaction to one batch so locks stay short. Use the DB connection pool assigned to workers.
- Rate-limit the upload endpoint.

**Acceptance criteria**
- See IMP-9. API p95 latency for other users stays within an agreed limit while several 50k imports run.

**Acceptance criteria**

## Main decision: build the CSV on the server

If the table loads data page by page, the browser only holds the current page. Building the CSV in the browser would export ~50 rows, not the full filtered list. A server endpoint that **runs the same filter logic as the list endpoint** is what makes "respects active filters" true by design, not just by testing. It also handles 10k rows easily if you stream the output.

(If the whole filtered dataset is already loaded in the browser, building the CSV there is a fine and simpler choice. Tasks 2–3 below would shrink to a small helper function.)

## Tasks

**1. Share the filter logic** (backend, ~0.5d)
- Move the orders list's filter/sort query building into one shared function, if it isn't already.
- The list endpoint and the export endpoint both call it. This prevents the two from drifting apart.

**2. Export endpoint** (backend, ~1d)
- `GET /orders/export?<same filter params>&columns=id,status,total,...`
- Allow only column keys from a server-side list (column key → header label + formatter). Reject unknown keys.
- Stream rows (DB cursor or batches of ~1000) straight into the response instead of building the whole file in memory.

**3. CSV formatting** (backend, ~0.5d)

**4. Frontend button** (~0.5d)

- Backend unit tests: escaping, formula-injection guard, column allow-list, filename date.
